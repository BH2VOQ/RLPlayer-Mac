# 「此前假绿、现已修正」判据清单（累计维护）

本文件是**判据本身的缺陷史**，不是产品缺陷史。每一条都记：原来的判据写了什么、
它实际上证明了什么、为什么不够、换成什么、以及**怎么证明新判据不是恒真**。

为什么值得单独维护：本项目铁律④是「测试通过 ≠ 测对了东西」。
这份清单是把那条铁律落成可复核记录的地方 —— 否则下一轮又会写出同型的假绿判据。

---

## 1. 诊断/反馈气泡：只验"搬进去"，不验"看得见"

- **原判据**：`auditDiagPopoverContent` 把控件搬进 NSPopover 的内容容器，然后遍历该容器
  断言 identifier 齐全；再 `auditRestoreDiagPopover` 搬回，断言 identifier 还在。
- **它证明了**：控件在两个容器之间搬动时没丢。
- **它证明不了**：气泡**显示出来**之后，这些控件在不在可视区内。
- **真实故障**：`RLPCardController` 只钉 `width=660`、没设 `preferredContentSize`，
  搬进去的 620pt 宽 NSScrollView 又没有父宽约束 ⟹ 气泡垂直塌陷成空框，用户看到一片空白。
- **新判据**：不点任何东西，直接遍历设置页真实子视图，判定
  「自身 + **全部祖先** hidden/alpha/frame 都通过」才算可见，再断言文案逐字、红底主按钮为 accent 色、
  页面上不存在 NSPopover 承载、也不存在 `sp_diagmore/sp_fbmore` 气泡入口。
- **新判据不是恒真的证明**：把同一批判据放回旧实现 → **215 passed / 12 failed**；
  新实现 → **230 passed / 0 failed**。

### 1b. 加强后的第一版判据**仍然是假绿**（这条最值得记）

第一版可见性写成 `b && !b.hidden && frame 有面积`。它在新旧代码上**都 PASS** ——
因为旧实现把控件放在 `hidden=YES` 的**容器**里，控件自身的 `hidden` 是 0。
改成 `RLPViewActuallyVisible()`（含祖先链）之后，旧实现从 4 FAIL 变成 12 FAIL，才真正抓住故障。

教训：**「元素可见」是一个链式属性，不是一个元素自己的属性。**

## 2. 底栏播放键：用 `image.name` 判图标是恒红的判据

- **原判据**：读 `playBtn.image.name`，`containsString:@"pause"`。
- **它证明了**：什么都没有 —— `+imageWithSystemSymbolName:` 生成的 NSImage，
  其 `name` 可能是 `nil`，判据在**正确实现上也会红**。
- **新判据**：对图标取**渲染位图指纹**（TIFF → PNG → NSData），
  断言「播放态位图 ≠ 暂停态位图」「停止后恢复到与初始同一张位图」。
- **新判据不是恒真的证明**：本项在旧提交上也是全绿（见下面第 6 条「回归防线」），
  所以它的价值是**防回退**而不是抓旧 bug。

教训：**判据要量「用户看得见的东西」（像素），不要量「我以为代表它的属性名」。**

## 3. EQ 页内层滚动：只数滚动条开关，证明不了"不可滚"

- **原判据**：遍历 EQ 子树，统计 `hasVerticalScroller || hasHorizontalScroller` 的数量 == 0。
- **它证明了**：没有人**打开**滚动条。
- **它证明不了**：这块区域不可滚。`NSScrollView` 即使 `hasVerticalScroller = NO`，
  只要 `documentView` 比可视区高，滚轮照样滚动它，事件照样在这里被吃掉。
- **新判据**：「可滚动」定义为 **①滚动条开关 OR ②内容确实超出可视区**（双条件，任一成立即算可滚）。
  再加**响应链可达性**：从 20 段表上的真实鼠标点沿 `nextResponder` 必须走到外层页面滚动容器，
  且链上不得出现第二个可滚动 scroll view。
- **新判据不是恒真的证明**：受控降级（把拆内层的几行 return 掉）→
  2 条红（`NSScrollView(v=1 h=0 overV=1)`），9 passed / 2 failed；恢复 → 11/11 绿。

## 4. EQ 曲线拖动：调内部方法只测了换算，没测事件能否到达

- **原判据**：直接调用 `-[RLPEQCurveView applyDragEvent:]`。
- **它证明了**：给定一个事件，频率/增益的换算公式是对的。
- **它证明不了**：真实鼠标事件能不能**走到**这个视图 ——
  被透明视图盖住、`hitTest` 返回值不对、不在 first responder 链上、
  坐标用了未翻转坐标系、被外层滚动容器截胡，这五类真实原因它一条都抓不到。
- **新判据**：`hitTest` 命中曲线 → 对命中视图直发 `mouseDown/mouseDragged/mouseUp` →
  断言 `/api/peq` **真的被下发**，且 URL 解码后 body 里**至少一段增益 ≠ 0**
  （后者专门防"发了请求但参数没变"这种最容易骗过判据的形态）。
- **为什么不用 `-[NSWindow sendEvent:]`**：实测窗口**未上屏**时 sendEvent 什么都不投递
  （hits=0；`makeKeyAndOrderFront` 之后 hits=1）。让测试弹真窗口会打扰用户，
  所以改用 `hitTest` + 对命中视图直发事件 —— 那正是 AppKit 在 sendEvent 内部做的两步。
  **权衡**：它验证了"事件能不能到达并生效"，但没有经过窗口服务层的坐标变换与事件队列。
  这条限制写在这里，不假装它等价于真机点击。
- **新判据不是恒真的证明**：受控降级（注释掉 `curve.onDragBand` 赋值）→
  2 条红（`posts=` 空），9 passed / 2 failed；恢复 → 11/11 绿。
- **更早的红证据**：在 `e0ec65f`（EQ 拖动尚未实现）上，这个测试**连编译都过不了**
  —— `setEmbeddedInPage:` 与曲线拖动在当时根本不存在。

## 5. 夹具自欺：索引写死的时长让"播放中"的断言全部跑在音频结束之后

- **现象**：`--audit` 里「底栏播放中图标」判据假红，`isPlaying=0`。
- **真因**：`BuildFixtureLibrary` 用 `say -o … "test"` 生成音频，实际时长 **0.69 秒**，
  而索引里写死 `dur = 30 + track` 秒。播放到第二次 0.5s 轮询时音频早已 EOS，
  底栏读到 `playing=false` 是**正确的**。
- **修法**：夹具改用重复文本拉长；索引里的 `dur` 改为用 `AVURLAsset` 读**真实时长**。
- **教训**：**夹具是判据的一部分。** 一个自欺的夹具可以让正确的实现永远红，
  也可以让错误的实现永远绿 —— 两种方向都会骗人。

## 7. 磨砂判据的两次失败尝试（第14项）

这条记的是**我写了两个不能用的判据**，最后怎么才算对。

**尝试 1：断言「加了 NSVisualEffectView 就算磨砂」** —— 纯类名判据，什么都没证明。

**尝试 2：换两张背景，断言条内像素随之变化** —— 看起来很像"真半透明"的证明，
但**在把玻璃层整个删掉之后依然 PASS（Δ=0.527）**。原因：播放条底色本身就是
`--barbg: rgba(246,246,249,.84)`（自带 84% alpha）。这条判据测的是**底色半透明**，不是磨砂，
作为磨砂判据是假绿。

**最终结论（实测后才知道的边界）**：离屏渲染路径下 AppKit **不做 backdrop 合成**：
- 单独 `cacheDisplayInRect:` 一个 NSVisualEffectView ⟹ 纯白 `sd=0.0000`；
- 渲染整个 contentView，**有玻璃层与没有玻璃层的结果逐字节相同**
  （高频棋盘背景下两次都 `sd=0.5000 / maxColGrad=0.1667`，图案原样透出、没被模糊）。

所以能测的只有结构（材质/层级/尺寸/圆角）与几何；**模糊本身必须由实机验收**。
这条写进 evidence 与报告，不假装离屏能证明磨砂。

## 8. 「连续两次随机 token 不同」抓不到 bug（第4批，真产品 bug）

- **原判据**：`generate_random_token(16)` 调两次，断言不相等。
- **它证明了**：这次没撞（漏检率取决于时钟精度）。
- **真实 bug**：token 生成是「拿 `high_resolution_clock` 当种子的 LCG」。
  单线程 20000 对撞 **0** 次 —— 单线程判据基本抓不到它。
  但 **4 线程各 2000 次**时，旧实现出现 **80 次碰撞**（8000 个里 7920 个唯一值）。
  这不是测试抖动：token 是 `/stream/<token>.wav` 的访问凭据，两个 UPnP 会话同时开流会撞到同一个凭据。
- **新判据**：多线程并发生成 8000 个 token，断言**零碰撞**。
  在旧实现上稳定红（实测碰撞 73–80 次），新实现（`arc4random`）稳定绿。
- **教训**：判据要按**真实并发形态**施压。单线程调两次的随机性断言，对"种子退化"这种缺陷几乎没有检出力。

## 9. 「几何判据全绿」不等于「渲染正确」（第12项，本轮新增）

- **判据**：第12项的结构 + 几何 19 项全绿（左内边距 16、按钮高 24、按钮间距 8、块间 14…）。
- **它证明的**：真实视图树里**帧矩形**符合规格。
- **漏掉的**：控件被压扁、文字截断、按钮被兄弟视图挤掉——这些在帧上仍可能"看起来合理"。
  第一次导出离屏对比图时发现：状态标签与两个按钮塞进同一个横向 `NSStackView` 并撑满卡片宽，
  状态文本的内在宽度把「预览写回」压成 0 宽、「执行写回」截断成「执行…」，而几何断言全部 PASS。
- **补强**：改回卡片的通用按钮行（`addButtonRow:`），并把**离屏渲染图**作为本项必交证据
  （`native-item12-before/after-20261113.png`）。教训：UI 判据要有一条"真的看一眼渲染结果"的路径，
  几何断言不能单独当交付证据。

## 10. 「属性存在」不等于「功能接入」（第8项，本轮新增）

- **上一轮的中间态**：`RLPTargetCurve` 数据表 + `RLPEQCurveView.targetCurve` 属性都写好了、
  能编译，看起来"目标曲线已接入"。
- **它证明的**：只有类型/属性存在。`targetCurve` **没有任何赋值点** ⟹ 图层永远是 nil，
  图上永远不画；UI 里也没有说明文字。这正是"假绿"的典型：代码存在、判据若只看属性就绿。
- **本轮判据**：用桩客户端驱动**真实 UI 动作链**（搜索 → 选型号 → 选预设 → 应用），
  断言①下拉框真的被填满 ②曲线视图**逐像素**变化 ③虚线列覆盖率 ④说明文案出现，
  红跑 10 项失败、绿跑 22 项全过。只断言属性/类名永远不会发现"没接线"。

## 11. 判据第一轮就抓到的两个真崩溃（第8项）

- `RLPMutableTargetCurve` 把父类 readonly 属性重声明为 readwrite，clang **不会**为它合成 setter
  ⟹ 构建通过、一运行就 `unrecognized selector` 崩溃。
- `targetCurve` 属性写成 `copy`，但 `RLPTargetCurve` 没实现 `NSCopying`
  ⟹ 赋值即 `copyWithZone:` unrecognized selector 崩溃。
- 两条都是"编译绿、运行崩"。教训：**构建绿不能当功能绿**，必须有真实运行路径。
