## 1. #13 到底指什么（先纠正一处容易误解的地方）

`docs/native-ui/PLAN.md` §7.1 原文：

> 「聆听模式 / 专业模式」是 **web 没有的发明**，会让「web 有的我是否都有」无法机械验证。
> 本轮把它整层拆掉（枚举 / 顶栏切换 / 侧栏分叉 / 设置页签随模式 / 工作台首页），
> 留档在 `dualmode-baseline-1.1.7.5`（tag）与 `archive/dualmode-1.1.7.5`（分支）。
> 双模式留到 parity 全绿之后，作为**薄表现层**回归（**不改变页面与控件集合**）。

所以：#13 **不是**「原生 / web 双模式」（那是 #12，已按你的决定定为「原生为默认且最终形态」），
而是把 **聆听模式 / 专业模式** 作为一层**纯呈现**重新加回来。

即这一层从设计上就要求「换模式只改入口排布，不改可用功能集合」。这就是 PLAN 说的"薄表现层"。

## 4. 为什么"重新加回来"现在风险大于收益

1. **会冲撞可见性判据**：`rlplayer_native --audit` 的 246 项与 203 项 ctest 里大量断言
   「某控件存在且可见」（如本轮刚加的 `npVolKnob`、`volFloor`、`barVolInput`）。
   一旦某模式默认隐藏部分入口，这些断言会在"非默认模式"下失败，或被迫放宽 —— 那是**判据质量的倒退**。
2. **收益面未定义**：web 版没有这一层；你本轮的要求是「按 web / windows 版对照移植」。
   把 web 没有的模式加回来，与"逐行对照"方向相反。
3. **同一件事做过一次并回滚**：2026-11-12 那一轮拆它，正是因为「web 有的我是否都有」无法机械验证。
   现在 parity 机制（`parity_scan` / `behavior_scan` / `theme_parity`）已经建成并全绿，
   但"模式 × 页面"的组合会把验证空间乘 2（11 页 × 2 模式 × 10 设置页签的可见性矩阵）。

## 5. 若仍要做：最小安全形态（建议方案，不在本轮实施）

| 要点 | 具体做法 |
|---|---|
| 单一状态 | 一个 `RLPUiMode`（`listening` / `studio`）存 settings，默认 `studio`（= 现状，不做行为变化） |
| 纯呈现 | 只做**入口过滤**：同一套 `RLPSettingsTabKeys()` 与侧栏 key 集合，按模式取子集；不可达的功能必须在另一模式可达（沿用归档那条纪律） |
| 判据不受影响 | audit / ctest 一律在「全可见」测试态下跑（提供 `RLPUiModeAll` 或测试注入），生产默认模式下才过滤 |
| 可回滚 | 与 web 无关，纯原生层；`RL_WEB_APP=1` 对照包保持不变 |
| 规模预估 | 侧栏或设置页各 1 处过滤 + 1 个枚举/持久化 + 判据注入 ≈ 150~250 行，**一个包可完成** |

1. **两个模式各自要"少看到什么"**？归档给的是「聆听模式没有工作台、设置挂全 11 页」；
   现在工作台已并入设置页（web 结构），这条差异是否还需要？

3. **是否要顶栏可见的切换控件**？web 没有；加了会重新引入"web 没有的发明"。
