# WIP-D：D1 卷积 DLL 设备缓冲复用 + 生产粒度复测（外部评审会话 D 包）

日期：2026-10-26 实测（工作区 `D:\RTA-health`，分支 `audio-health`；探针 `tools/gpu_precision.cpp`）
状态：HIP 侧全部为本机实测（含铁律 5 双门）；CUDA 侧同构修改、未编译未实测（见 §7）。

## 1. 一句话结论

D1 缓冲复用已落地且**零精度回退**（16 格矩阵逐格与修复前完全一致、恒等门同值 1.979e-08、
升频同值 3.331e-16），但**生产粒度（4096 样/块）耗时与修复前持平**（16 块 30.8→31.0 ms 中位，
差在运行噪声内）——实测证明本驱动上每调用 hipMalloc/hipFree 有缓存、**本就廉价，分配从来不是
瓶颈**；剩余固定开销是每调用的 H 频谱上传（IR=65536 时约 1 MB H2D）+ CPU 侧 IR 分区 FFT 重算
+ 同步。**4096 块粒度 GPU 仍慢 ~3.3×，A 包「按 (irLen, chunkSize) 门控」建议维持不变。**

## 2. 改动说明

| 文件 | 改动 |
|---|---|
| `src/gpu/gpu_conv_hip.cpp` | `rta_gpu_convolve` 三处每次 hipMalloc/hipFree → static 缓冲池（仿 `gpu_resample_hip.cpp`）：`dH/dX/dY` + 各自 `cap`，仅 `!dH \|\| size>cap` 时「先 free 旧再 malloc 新」（选这个顺序：长 IR 时 H 一块 MB 量级，先分配新会两份瞬时并存把显存翻倍）；**只增不减**；malloc 失败返回 2，调用方（gpu_bridge.h）退 CPU。`!dH` 条件是失败恢复关键：扩容失败时指针已空而 cap 还是旧值，没有它后续小请求会拿空缓冲 memcpy。文件头加 D1 段（原因数字 + 策略 + 复测结论）。线程前提与 resample 相同：生产管线卷积在单一生产者线程串行调用，池无并发访问，static 不加锁。 |

| `tools/gpu_precision.cpp` | 生产粒度节新增「IR=65536、块 4096、**串 64 块**（稳态）」一行；原 16 块行保留作对照。到该节时矩阵已把缓冲养到最大容量，稳态测量不触发重分配。 |

## 3. 重编配方与铁律 5 双门

### 3.1 配方（两次修正，全程如实记录）

spec 给的命令 `hipcc --offload-arch=gfx1201 -O3 -shared -Isrc src/gpu/gpu_conv_hip.cpp -o ...`
实测**不够**，踩了两个坑，都由探针暴露而非编译器报错：

1. **只编卷积单文件 → DLL 丢失 resample 导出**。旧 DLL 导出表 4 个符号
   （rta_gpu_available / rta_gpu_convolve / **rta_gpu_resample / rta_gpu_resample_invalidate**），
   单文件编译只剩 2 个 → 探针升频节直接「GPU 升频不可用」（修复前明明有 3.331e-16 的结果）。
   修正：补编 `src/gpu/gpu_resample_hip.cpp`（该 DLL 一直由两个源组成，见 `tools/build_gpu.ps1` 第 31 行）。
2. **缺 `-march=x86-64-v2` → host 侧 FFT 代码生成退化，GPU 路径全线 +20%**。正式配方
   `tools/build_gpu.ps1` 一直带此 flag（spec 命令没有）。实测缺它时：矩阵段每格 +3~6 ms、
   16 块 31.1→37.9 ms、64 块 125.6→154.4 ms；换 `-O2` 仍慢（40.2 ms）排除优化级别因素；
   补上 `-march=x86-64-v2` 后全部恢复基线（归因实验见 §5）。

**最终配方**（= build_gpu.ps1 的 flag + 显式单 arch gfx1201，满足铁律 5）：

```
"C:/Program Files/AMD/ROCm/7.2/bin/hipcc.exe" --offload-arch=gfx1201 -O3 -march=x86-64-v2 \
    -shared -Isrc src/gpu/gpu_conv_hip.cpp src/gpu/gpu_resample_hip.cpp -o build-health/rtagpu.dll
```

- hipcc 路径：spec 预判正确，就在 `C:/Program Files/AMD/ROCm/7.2/bin/`（hipcc.exe，另有 hipcc.bat）。
- 编译警告只有既有类别：`__declspec(dllexport) is not supported` 只出现在 **device 编译遍**
  （gfx1201），host 遍正常导出——llvm-objdump -p 确认 4 个导出全在；kaiser.h/fft.h 的 C++17
  extension 警告为存量。无新增警告。
- 探针重建：`"C:/Program Files/AMD/ROCm/7.2/bin/clang++.exe" -O2 -std=c++17 -Isrc tools/gpu_precision.cpp -o build-health/gpu_precision.exe`。
- 产物：`build-health/rtagpu.dll` 184,320 字节（旧 577,024 = build_gpu.ps1 的 24-arch fatbin；
  本地验证用单 arch，出包仍走脚本，见 §8.2）。

## 5. 生产粒度复测（每块 4096 样，生产者 kChunk）

| 配置 | 16 块 @IR=65536 | 16 块 @IR=262144 | 64 块 @IR=65536（稳态） |
|---|---:|---:|---:|
| A 包基线（2026-10-25） | 30.8 ms | 92.4 ms | — |
| 修复前旧 DLL（本轮 01:33） | 32.2 ms | 95.7 ms | **125.6 ms** |
| 修复前旧 DLL（01:39 复跑） | 31.1 ms | 91.8 ms | — |
| **修复后新 DLL**（3 轮） | 30.0 / 33.5 / 31.0（中位 **31.0**） | 93.4 / 93.6 / 91.9（中位 **93.4**） | 121.6 / 124.5（中位 **123.0**） |
| GPU/CPU（修复后 64 块） | — | — | **~3.4× 慢**（1.90 vs 0.56 ms/块） |

**判读**：
1. 复用前后差 ≤3%，而本会话同一二进制的运行间噪声就有 ±5~10%（CPU 侧同一探针合计耗时
   实测 9→42 ms 波动，桌面有背景负载）。**只能断言「无可测回退」，不能断言有 3% 收益。**
2. A 包「hipMalloc/hipFree 是 3× 慢的主因」这一猜测**被实测否定**：去掉每调用 3×malloc+3×free
   后耗时不动 ⟹ 本驱动对刚释放的尺寸有分配缓存，malloc 本就廉价（每调用 ≪30 μs）。
3. 剩余固定开销解剖（IR=65536、B=1024，每调用）：H 频谱 H2D 上传 **1.0 MB**
   （P·fftN·8B = 64×2048×8）+ CPU 侧 64 次 2048 点 IR 分区 FFT 重算 + X/Y 各 64 KB 拷贝 +
   kernel + 同步 ≈ 1.9 ms/块；CPU 流式路径 0.56 ms/块。
4. **结论维持 A 包建议**：卷积 GPU 只应在「单块 ≥65536 样且 IR ≥65536」时开启（A 包 §3：
   2~14×），4096 块粒度走 CPU。下一步候选（**超出 D1 范围，未实施**）：仿 resample 相位表
   按 (irLen, B) 把 H 固化在显存、失效时才重传——可同时消掉 1 MB/调用上传与 host FFT 重算，
   4096 粒度才有可能翻盘。

## 6. 归因实验记录（为什么 +20% 不是缓冲池的锅）

中途两轮（01:36/01:41）曾出现全线 +20%（64 块 148~154 ms），按铁律 3 追查而非放过：

| 步骤 | DLL | 64 块 GPU | 结论 |
|---|---|---:|---|
| 1 | 旧 DLL 复跑（01:39） | 125.6 →（复跑16块31.1） | 排除机器漂移（旧 DLL 稳定 31~32） |
| 2 | 新代码 `-O3` 无 `-march` | 154.4 | 慢，复现 |
| 3 | 新代码 `-O2` 无 `-march` | 16 块 40.2 | 仍慢 ⟹ 不是 O2/O3 之差 |
| 4 | 新代码 `-O3 -march=x86-64-v2` | 121.6 / 124.5 | **恢复** ⟹ 元凶是缺 `-march`（host FFT 代码生成），与缓冲池无关 |

慢的增量分布与「DLL 内 CPU FFT 变换数量×规模」成正比（1024 点格 +3 ms、2048 点/块 +0.44 ms、
8192 点格 +6 ms），与「host 编译基线从 x86-64-v2 掉到 SSE2」的机理吻合。
