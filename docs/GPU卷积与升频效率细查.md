# GPU 卷积 / GPU 升频 效率细查（2026-10-26）

> 机器：Apple M4 / macOS 27.0.1 / arm64
> 后端：`librtagpu.dylib`（Metal，运行时编译 MSL）
> 方法：独立探针直接调 `GpuBridge` + `StreamingConvolver`，20 次取平均，warmup 后计时
> 生产口径：`kChunk=4096`（`tools/rtaweb.cpp:3038`），`block=1024`（`pipeline.h:78`）

---

## 0. 一句话结论

**GPU 卷积在生产形态下全面亏损（慢 3.4~8.3 倍），根因是「每块 4096 样」远低于 GPU 的盈亏平衡点
（实测 n≥32768 才翻盘）；而 GPU 升频大幅占优（快 5~29 倍），因为升频是纯算力活、不吃块大小。**

---

## 1. GPU 卷积：拐点在 n≈32768，生产只有 4096

### 1.1 扫 n 找盈亏平衡点

| IR | 每块 n | GPU | CPU | GPU/CPU | 判定 |
|---:|---:|---:|---:|---:|---|
| 16384 | 4096 | 0.891 ms | 0.264 ms | **3.37x** | GPU 慢 |
| 16384 | 16384 | 1.539 | 1.098 | 1.40x | GPU 慢 |
| 16384 | 32768 | 2.619 | 2.115 | 1.24x | GPU 慢 |
| 16384 | **65536** | 4.108 | 4.332 | **0.95x** | **GPU 胜** |
| 16384 | 262144 | 12.591 | 17.101 | 0.74x | GPU 胜 |
| 65536 | 4096 | 2.088 | 0.520 | **4.02x** | GPU 慢 |
| 65536 | 16384 | 2.687 | 2.119 | 1.27x | GPU 慢 |
| 65536 | **32768** | 3.351 | 4.487 | **0.75x** | **GPU 胜** |
| 65536 | 65536 | 5.145 | 8.838 | 0.58x | GPU 胜 |
| 65536 | 262144 | 16.319 | 34.778 | 0.47x | GPU 胜 |

**盈亏平衡点约在 n = 32k~64k**。生产每块只有 **4096** ⟹ 差 8~16 倍，GPU 必亏。

### 1.2 为什么小块必亏（机理）

`gpu_metal.mm` 的既定取舍（`:58-80`）：**FFT/IFFT 留在 CPU 做 double，GPU 只做逐点复数乘加**。

每次 `rta_gpu_convolve` 调用的固定开销：
1. CPU 侧算 IR 的 FFT（**每块都重算**，见 §1.3）
2. CPU 侧算本块输入的 FFT
3. 提交 MTLCommandBuffer + **`waitUntilCompleted`（同步阻塞）**
4. CPU 侧 IFFT + overlap-add

n=4096 时，第 3 步的提交/等待是**纯固定成本**，而第 4 步的乘加量太小摊不平它。

### 1.3 附带的浪费：IR 的 FFT 每块重算

IR 在整曲播放期间**不变**，但 `gpu_metal.mm:452-466` 每次调用都重算 P 次 FFT：

| IR | P | IR-FFT 占 GPU 调用 | 说明 |
|---:|---:|---:|---|
| 1024 | 1 | 7.6% | 影响小 |
| 65536 | 64 | **63.5%** | 大头 |
| 262144 | 256 | **91.3%** | 几乎全是浪费 |

**这是可以消除的浪费**（缓存 IR 频谱），但见 §1.4 —— 消掉之后**仍然不够翻盘**。

### 1.4 即使缓存 IR 的 FFT，生产形态仍然全亏

按 overlap-save 修好后的真实输入量（`n' = 4096 + irLen-1`）评估：

| IR | 每块输入 | GPU(现状) | GPU(缓存IR后) | CPU | 缓存后仍慢 |
|---:|---:|---:|---:|---:|---:|
| 1024 | 5119 | 0.725 | 0.700 | 0.190 | **3.69x** |
| 4096 | 8191 | 0.960 | 0.868 | 0.197 | **4.41x** |
| 16384 | 20479 | 1.734 | 1.163 | 0.284 | **4.09x** |
| 65536 | 69631 | 5.310 | 3.915 | 0.518 | **7.55x** |
| 262144 | 266239 | 20.839 | 15.090 | 1.821 | **8.29x** |

⟹ **缓存 IR 频谱能把 GPU 调用砍掉一半以上，但生产形态下仍慢 3.7~8.3 倍。**
根因不是「有浪费」，而是**「GPU 只做乘加、FFT 全在 CPU」这个架构在 4096 块长下根本不成立**。

### 1.5 真正的解法（若要 GPU 卷积真的有用）

必须**把 FFT 也搬上 GPU**（`gpu_metal.mm:79-80` 已写为「后续应该做」）。那样：
- 每块只需 1 次提交（而非 4 步 CPU↔GPU 往返）
- FFT 的 O(N log N) 也吃到 GPU 并行
- 但需要手写 MSL radix-2 FFT，易错，且要重新验证数值

**在没做这件事之前，GPU 卷积在 mac 上应视为「默认关闭」的功能。**

## 2. GPU 升频：为什么快 5~29 倍

| 转换 | CPU | GPU | GPU/CPU |
|---|---:|---:|---:|
| 44.1k → 352800 | 597.9 ms | 16.8 ms | **0.028x（快 29 倍）** |
| 44.1k → 384000 | 21.2 ms | 4.1 ms | **0.192x（快 5.5 倍）** |

**为什么与卷积相反**：
- 升频每输出样要做 **T 次乘加**（T=512~32768），是**纯算力活** ⟹ 块小也不怕，工作量本身就大
- 卷积在 4096 块下，GPU 能并行的那部分（乘加）**量太小**，被固定开销吃掉

⟹ **结论：升频该走 GPU，卷积不该走 GPU。** 这两个不能一概而论。

## 3. 对 `irgpu` 开关的建议

现状：`p.convGpu` 默认 `false`（`rtaweb.cpp:312`）⟹ 默认不吃亏。

三个选项：

| 选项 | 做法 | 代价 |
|---|---|---|
| **A. 保持默认关（推荐）** | 不动代码，用户开 `irgpu=1` 时仍可工作（正确但慢） | 无 |
| B. UI 标注「mac 上不建议开」 | 在设置页 `irgpu` 旁边加提示 | 一行前端改动 |
| C. 按 IR/n 门控 | 只在 n≥32768 时走 GPU | 生产 n 恒 4096 ⟹ **门控等于永久关闭**，且掩盖了「架构不成立」这个真因 |

**建议 A + B**：功能保留（铁律：功能不删），但明确告知用户 mac 上卷积走 GPU 是净亏。
**不建议 C**：它看起来像"优化"，实际是永久禁用，还会让后来人误以为「门控做过了就没事了」。

## 4. 与既有文档的差异（需要修正）

`gpu_metal.mm:70-76` 记录（2026-10-25 实测，`n=32768`）：
```
irLen=1024  (P=1)  → 1.26x   GPU 更慢 26%
irLen=4096  (P=4)  → 1.25x   GPU 更慢 25%
irLen=16384 (P=16) → 0.84x   GPU 快 16%
irLen=65536 (P=64) → 0.84x   GPU 快 16%
```
**这份数字是对的，但口径是 n=32768**（一次吃 32768 样）。
本次实测在 n=32768 时同样得到 GPU 胜（IR=65536 → 0.75x），**与既有记录一致**。

⟹ **既有注释没错，但容易被误读成「mac 上卷积能加速」**。生产是 n=4096，结论相反。
建议在注释里补一行：`⚠️ 生产 kChunk=4096 时上述收益全部消失，实测慢 3.4~8.3 倍`。
